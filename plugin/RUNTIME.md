# Применение плана в установленном STE

Проверен **STE Slicer 7.10.12**, Python **3.5.7**, NumPy **1.15.4**,
Qt **5.10.0**, машина `hte530v5.2.4`. Проверка использует настоящий Qt и
штатный CuraEngine в headless-процессе установленной программы. Это не ручная
приёмка интерфейса и не испытание отпечатка.

`STEPlannerRuntime` — расширение Uranium, `ste_planner/runtime_adapter.py` —
транзакция применения. Меню `Apply planner decision…` открывает JSON решения.
При установке расширения положите рядом с его `__init__.py` и
`RuntimeExtension.py` копию пакета `ste_planner`. Современный worker остаётся
отдельным процессом; Gmsh/SciPy во встроенное окружение не устанавливаются.

Для обычного чата используется установленный `AIAssistant`:
`list_model_sources → plan_print → apply_plan → verify_plan → slice → export`.
Источники выбираются по серверному attachment_id, object_id сцены или реальному
абсолютному пути. Object input читает исходный STL, не текущий transform.
`list_objects` возвращает source_path/exists/format и world_transform_printer.
Для object_id переиспользуется тот же единственный объект; его STL и штатное
центрирование проверяются до изменения сцены. Дополнительные объекты, модификаторы
и per-object overrides не удаляются: для них есть отдельное применение общих
настроек проекта без перемещения. Без target_node загрузка STL требует пустой сцены.
Проверка: `python plugin/tools/check_ai_assistant_runtime.py` — HTTP upload,
оба вида ID, нативная нарезка/экспорт и единый Undo/Redo в отдельном профиле.
Браузерный профиль активного чата в тестовый STE не копируется.

Writers G-code/3MF вызываются из фонового потока: их штатные Qt-callback не должны
ждать заблокированный собственным вызовом Qt. После apply фактические настройки
проверяются canonical readback, а неизменность геометрии — отдельным scene hash;
отложенная замена эквивалентного служебного id контейнера не является изменением STL.

Решение с `base_presets` применяется реальными контейнерами quality_changes/quality/
material/variant/definition_changes со сверкой их хешей; в user пишется только Δ, readback
сверяет значения и id контейнеров стеков ([PRESETS.md](PRESETS.md)). Решения без
`base_presets` применяются прежним `Planner process profile`. Режим native-пресетов в
настоящем STE проверен на исходном пыльнике, включая применение в текущей сцене.

Нативная проверка текущего проекта:
`python plugin/tools/check_ai_assistant_runtime.py --existing-project`.
Она загружает исходные STL/DOCX, редактирует положение и поворот, сохраняет
идентичность node, применяет native-пресет одной операцией, проверяет readback,
нарезку и экспорт, затем сравнивает состояние до/после Undo/Redo.

Для анализа семи исходных деталей добавлен `analysis_only`: в изолированном
профиле доступны нативные Spiral/Full и экспорт их траекторий. GUI-применение
сохраняет ограничение 5D до отдельного подтверждения кинематики. Исправлено
представление треугольников для двойной индексации CLIParserBackend, а ошибки
Boolean теперь блокируют зачёт fallback-результата. Дочерние движки ограничены
Windows Job Object конкретного запуска и завершаются вместе с ним.
Актуальные реальные проверки: [TOOLPATH_PHYSICS.md](TOOLPATH_PHYSICS.md).

Адаптер проверяет исходный SHA-256 STL, машину, материал, режим, ориентацию,
согласованность compiled patch с ожидаемыми значениями и замкнутость объёмов.
Он отказывает при существующей модели в проекте, поскольку изменение глобальных
настроек затронуло бы её. Ошибочное применение откатывает контейнеры и сцену
до добавления операции в Undo. Успешное применение поддерживает Undo/Redo.

Оси преобразуются один раз: `(X,Y,Z) -> (X,Z,-Y)`. Уже размещённые объёмы
переводятся в локальные координаты родителя. Начало координат стола добавляет
движок. Для партии создаются отдельные модели с дочерними модификаторами.

Обязателен readback всех `planner.READBACK_KEYS`, включая `functional.PROCESS_KEYS`,
параметры поддержек и производные значения. Проверяется **активный backend**,
а также идентичность машины и material container. STE 7.10 отправляет сигналы
смены контейнеров асинхронно: адаптер вызывает штатный обработчик выбора движка
и ждёт стабилизации настроек перед `forceSlice`. Неизвестный API приводит к отказу.

Enforcer использует `support_mesh=True`, `support_mesh_drop_down=True`, blocker —
`anti_overhang_mesh=True`. Запреты расширяются на XY-зазор поддержки, радиус
линии и геометрический резерв 0,01 мм; глубина учитывает зазор по Z и округление
слоёв. Enforcer уменьшается у границ, чтобы его приоритет в движке не восстановил
поддержку у защищённого края. Слишком узкая зона получает предупреждение;
полнота опирания и прочность поддержки этим не подтверждаются.

## Воспроизведение на Windows

Укажите `STE_RESOURCES_DIR` на `resources` установленной версии. Из корня:

```powershell
.\.venv-functional\Scripts\python.exe plugin/tools/plan_functional.py experiments/functional_artifacts/beam.stl experiments/functional_artifacts/beam_task.txt --spec experiments/functional_artifacts/beam_spec.json --surfaces experiments/functional_artifacts/beam_surfaces.json --llm --mode classic --mesh-size 6 --output .runtime/live_functional_decision.json
.\.venv-functional\Scripts\python.exe experiments/check_ste_runtime.py
.\.venv-functional\Scripts\python.exe experiments/summarize_ste_runtime.py
```

`check_ste_runtime.py` клонирует профиль в игнорируемую `.runtime/`, запускает
изолированные экземпляры STE и сохраняет артефакты в `experiments/ste_runtime/final/`.
Открытый пользовательский проект не меняется. Для запуска нужен уже настроенный
профиль указанной машины. `--prepare-only` создаёт входы; `--case` повторяет один
сценарий. Сводный скрипт завершается с ошибкой при нарушении проверяемого условия,
включая геометрический контакт поддержки или нарушение Undo/Redo.

Сравниваются обычный профиль, живая LLM-демонстрация, enforcer, blocker, партия
из двух моделей и отказы SHA/readback/5D/существующий проект. G-code и 3MF имеют
SHA-256; проект проверяется как ZIP, решения сверяются по каноническому хешу.
Вместо нестабильного совокупного bounding box STE сохраняются матрицы, границы
собственных сеток, их хеши и фактические флаги модификаторов.

Сводка: [отчёт](../experiments/ste_runtime_report.md),
[метрики](../experiments/ste_runtime_results.json).

## Границы подтверждения

Температуры в G-code — заданные значения, время/филамент — оценки движка.
Без измеренного `Q_limit` проверка потока остаётся `unknown`. Непрерывность
слоёв, завершение программы и достижение высоты модели проверяются отдельно
от заявленного числа слоёв: расхождение заголовка остаётся `unknown`, а не pass.
Пространственный G92 требует преобразования координат; неизвестность сохраняется.

Проверка контакта использует реальные экструдирующие отрезки и их радиус,
зазор по Z и треугольники контролируемой горизонтальной поверхности. Комментарии
TYPE только определяют тип пути. Общее отсутствие контакта на произвольной
криволинейной поверхности, покрытие/несущая способность поддержек и физическая
шероховатость не доказаны.

Spiral/Full отказываются применять даже в демонстрации без реальной кинематики,
головки/оправки и проверки полной траектории. `software_fixture` сохраняет
`applied=False`; её применение разрешено только в подтверждённом изолированном
профиле. Никакой тест не повышает решение до `qualified`.
