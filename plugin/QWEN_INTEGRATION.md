# Совместная работа ядра STE Planner, Qwen и DoubleML

## Ответственность компонентов

Qwen извлекает требования с цитатами, выбирает доступные инструменты и предлагает объяснение. Ядро извлекает исходные величины, проверяет предложения, рассчитывает варианты, компилирует настройки и определяет статус. Причинный DoubleML оценивает эффект изменения параметра в области данных при предпосылках идентификации. Оценка причинного эффекта не является прогнозом абсолютной прочности конкретной детали.

Текущая реализация интегрирует офлайн-планировщик. MCP HTTP-сервер, пользовательский чат, изменение Qt-сцены, настоящий слайсинг и экспорт остаются отдельным этапом.

## Публичный интерфейс

```python
from ste_planner.qwen_client import QwenClient
from ste_planner.qwen_assistant import PlanningAssistant

client = QwenClient.from_env(".env")
assistant = PlanningAssistant(client)
result = assistant.run(tz_text, selected_stl_path,
                       planner_options={"source": "task.docx"})
decision = result["decision"]
```

`planner.plan_case(..., llm_items=...)` остаётся доступен отдельно, без сети. Старые вызовы без `llm_items` сохраняют поведение.

В `run` пути и конфигурацию задаёт приложение. Qwen не может заменить путь STL, прочитать файл окружения, выполнить Python, выбрать endpoint причинной модели или записать настройки. История принимается только как недоверенные текстовые сообщения, без сторонних system/tool-инструкций. Основные ответы:

- `decision`: результат ядра с patch, статусами, provenance и планом испытаний;
- `explanation`: детерминированное объяснение ядра;
- `assistant_text`: текст Qwen, помеченный `assistant_text_verified=false`;
- `events`: последовательность инструментов и их структурированные результаты;
- `causal_estimates`: эффекты с указанием области и неопределённости;
- `llm_error`: безопасная диагностика, без токена и тела ошибки провайдера;
- `execution_scope=offline_planning_no_slicer_writes`.

При ошибке сети, неподдержанном tool calling или исчерпании бюджета возвращается доступное решение ядра и ошибка LLM. Это fallback, а не успешная проверка Qwen. Ограничения по умолчанию: 6 раундов, 12 вызовов инструментов, конечный размер входов/ответов.

## Инструменты Qwen

1. `propose_requirements(items)`: цитаты привязаны к текущему тексту. Неизвестные поля, NaN, неверные единицы и подмена направления не принимаются. `value_as_written` не разрешён во внешнем контракте. Не подтверждённое правилами значение свойства получает assumed и не становится обязательным.
2. `plan_print()`: основной планировщик; аргументы путей и произвольных настроек отсутствуют. Первые этапы extraction и planning запрашиваются через явный tool_choice, а не только текстовый prompt.
3. `list_causal_models()`: доступные модели и их области; при отсутствии — пустой список.
4. `estimate_setting_effect(model_id,treatment,outcome,to_value)`: исходное значение, единицы и контекст берутся из решения ядра/компилятора, не из аргументов Qwen. В частности, infill/flow в effective settings — проценты, а не доли; единицы causal-модели обязаны совпасть. Полученный эффект не изменяет patch и не является разрешением применить новую настройку. Для изменённой конфигурации нужен новый проверенный расчёт.

Текст ТЗ рассматривается как данные. Prompt injection в нём не даёт доступ к новым инструментам. Семантическая проверка требований консервативна и не является полным пониманием естественного языка: обязательные выводы нужно проверять по `requirements`, `verification` и `trace`.

## Контракт с добавляемым DoubleML

Тренировку выполнять в подходящем внешнем окружении. В слайсер Python 3.5 не устанавливаются DoubleML/scikit-learn и не загружаются непроверенные pickle. Адаптер ядра `causal_bridge` использует только числовую сводку уже обученной одиночной `DoubleMLPLR`.

Для PLR принимается постоянный линейный эффект. Контраст: `effect=theta*(d_after-d_before)`. Границы доверительного интервала коэффициента умножаются на ту же разность и сортируются, включая отрицательное изменение. Это интервал оценённого контраста при предпосылках модели; он не является prediction interval индивидуальной детали. IRM, PLIV, многомерные вмешательства и CATE нельзя подставлять в этот контракт.

Доверенный код обучающего компонента:

```python
from ste_planner.causal_bridge import PLREffect, CausalRegistry

bridge = PLREffect.from_fitted_doubleml(
    fitted_plr,
    model_id="qualified-training-run/version-id",
    treatment="material_print_temperature", treatment_unit="degC",
    outcome="tensile_strength", outcome_unit="MPa",
    treatment_bounds=reviewed_temperature_support,
    context=reviewed_context,
    identification_reviewed=identification_reviewed,
    support_reviewed=support_reviewed,
    level=0.95)
registry = CausalRegistry([bridge])

# Перенос во встроенный Python слайсера без pickle и зависимостей DoubleML:
import json
with open("reviewed_effects.json", "w") as handle:
    json.dump([bridge.to_record()], handle, allow_nan=False)
```

`reviewed_context` обязательно содержит `machine_id`, `material_id`, `mode`, `nozzle_mm`. Для передачи в текущий агент эти четыре поля должны точно совпасть с контекстом решения. Модели с дополнительными контекстными условиями консервативно не применяются, пока приложение не предоставит подтверждённые значения этих полей. Интервал параметра — проверенная область поддержки, а не просто min/max всех сырых наблюдений.

Имя treatment должно совпасть с единственным индексом строки `fitted_plr.confint()`; модель должна иметь единственный конечный коэффициент и согласованный CI. `params_names` в DoubleML содержит имена вспомогательных моделей, а не treatment. Метаданные и рецензирование предпосылок задаются обучающим компонентом, не Qwen. В частности, необходимы проверка confounders и отсутствия недопустимого post-treatment adjustment, корректные cross-fitting/группировки, достаточная вариация treatment и применимость линейного эффекта. Прямоугольная проверка области в адаптере не доказывает overlap.

Контракт `confint()` сверён с [официальной реализацией DoubleML](https://github.com/DoubleML/doubleml-for-py/blob/main/doubleml/double_ml.py): строки результата индексируются именами treatment. Тест экспорта использует имитацию этого интерфейса; обучение настоящей DoubleMLPLR в текущую проверку не входит.

Для обмена между разными интерпретаторами экспортируйте сводку в JSON с полями конструктора `PLREffect`: `model_id`, `treatment`, `treatment_unit`, `outcome`, `outcome_unit`, `coefficient`, `confidence_interval`, `treatment_bounds`, `context`, `identification_reviewed`, `support_reviewed`, `level`. Версия, обучающий прогон и связанные отчёты должны однозначно идентифицироваться `model_id`. CLI принимает такой список через `--causal-models path/to/reviewed_exports.json`.

Доверенные модели регистрируются при создании `PlanningAssistant(client, registry)`. Без модели результат — needs_calibration. При другом материале/режиме/сопле или за пределами treatment support — out_of_domain. Если предпосылки ещё не рассмотрены — unknown. Даже вычисленный эффект имеет `absolute_prediction=false`, `setting_approval=false`.

## Настройки и ключ

Поддерживаются существующие `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL`; специализированные `TIMEWEB_API_KEY`, `QWEN_BASE_URL`, `QWEN_MODEL` имеют приоритет, если заполнены. Переменные окружения имеют приоритет над одноимёнными записями файла. При смешивании алиасов используйте один согласованный набор. Файл читается только явно, без выполнения shell-подстановок и без изменения процесса через импорт модуля.

`QWEN_TIMEOUT` ограничен 300 секундами; redirect с Authorization запрещён. HTTPS, цепочка сертификатов и имя сервера проверяются. Дополнительный доверенный CA задаётся `QWEN_CA_FILE`; на Windows доверенные ROOT читаются из системного хранилища. Ключ не включается в запросы messages, результаты и диагностические отчёты. Сырой ответ провайдера при ошибке не выводится.

Timeweb получает текст выбранного ТЗ и результаты инструментов, в том числе часть вычисленных свойств и настроек. STL остаётся локально. Вызывающее приложение должно учитывать согласие пользователя на такую передачу. Валидационный скрипт семи примеров запускается отдельно, а не автоматически при импорте или запуске тестов.

## Проверка

`tests/test_qwen_integration.py` проверяет HTTP-контракт, скрытие ключа, ошибки/обрезанные ответы, grounded merge, ошибки единиц и направления, причинный контраст, контекст, область действия, бюджет инструментов, fallback и передачу требований в настоящий планировщик. Значения коэффициентов в этих тестах синтетические; они не включаются в производственный каталог.

Тесты совместимы с `tools/run_py35_tests.py`. Реальные проверки сети выполняются `tools/qwen_plan.py --check-api`; семь ТЗ — `tools/validate_qwen_examples.py`. Машиночитаемый отчёт не сохраняет ключ и необработанный ответ Qwen. Наличие отчёта не означает физическую квалификацию изделия.

Первичные документы: [Timeweb AI Gateway](https://timeweb.cloud/docs/ai-gateway/manage), [модели DoubleML](https://docs.doubleml.org/stable/guide/models.html), [DoubleML workflow](https://docs.doubleml.org/stable/workflow/workflow.html). Конкретная доступность модели и tool calling проверяется живым запросом.

Адаптер передаёт `enable_thinking=false`: этот режим совместим с принудительным выбором функции и не требует передачи внутренних reasoning-сообщений. Основание: [документация Function Calling Qwen](https://help.aliyun.com/en/model-studio/qwen-function-calling). В текущем Timeweb-подключении режим проверяется отдельно от совместимости SDK. При изменении модели нужно повторить `--check-api`.

Уточнения пользователя становятся новыми исходными требованиями только после явного включения приложением в текущий текст ТЗ с указанием их происхождения. Текст `history` даёт Qwen контекст и не может молча перезаписать подтверждённые требования ядра.
