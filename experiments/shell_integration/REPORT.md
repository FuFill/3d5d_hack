# Lenaz + исходное ядро: проверка интеграции

## Текущий проект и native-пресеты, 24.10.2026

После изменений `8b0b624` проверена работа с уже открытой моделью в настоящем
STE 7.10.12. Последний полный набор: **260 pass, 1 skip**, включая 54 теста оболочки.
Машиночитаемое подтверждение: [current_project_report.json](current_project_report.json).
Результаты первоначальной интеграции ниже сохранены как исторический этап.

В нативном сценарии исходный пыльник организаторов загружен на стол, перемещён и
повёрнут вручную, исходное ТЗ DOCX прикреплено через HTTP. План применён к тому же
объекту (node identity сохранён), выбран штатный `Draft (draft)`, readback прошёл,
G-code/3MF экспортированы, Undo/Redo вернул исходное размещение/поворот и восстановил
план. Карточка вопроса и ответ проверены через HTTP; это проверка программного
протокола, а не измерение физически установленного материала. Timeweb-соединение прошло.

Нативные прогоны нашли две ошибки, не обнаруженные fakes:

- STE лениво удаляет неопределённые записи материала (`value=None`). Их отсутствие
  не означает изменение effective settings; теперь они исключены из каталога,
  заданные значения продолжают защищаться digest.
- Обычный загрузчик центрирует вершины STL. Допускается только исходный меш или
  точное штатное центрирование; сохранённый offset компенсируется в transform и
  локальных координатах модификаторов. Деформации, масштабирование и перестановка
  граней не выдаются за штатное центрирование.

Сопроводительная просьба пользователя больше не затирается текстом DOCX. Вопрос
регистрируется атомарно с публикацией, чтобы немедленный ответ UI не потерялся.
LLM получает положение до 0,001 мм и мировую матрицу в осях принтера.
Алгоритмы выбора/механики/DML в этой доработке не переписывались.

Воспроизведение текущей сцены:

```powershell
python plugin/tools/check_ai_assistant_runtime.py --existing-project
```

Ограничения: проверен один classic-кейс, а не все native-пресеты/5D; несколько
моделей, собственные модификаторы и per-object overrides не включаются скрыто в
orientation plan. Для общих настроек есть отдельный settings-only путь с сохранением
геометрии. Масштаб/поворот исходного STL планируются ядром, текущие пользовательские
трансформации не становятся новыми измерениями материала. Физическая квалификация
и оптимальность не заявляются; `physical_print_approval=false`.

## Первоначальная интеграция

24.10.2026. В `main` сначала опубликован `c006fd3`, затем слита ветка Lenaz
(`3b6c9ce`). Исходные файлы `plugin/ste_planner` не изменялись.

Оболочка использует `plan_case` в современном worker, хранит решение под собственным
`plan_id`, применяет его через исходный `runtime_adapter.create_operation` в Qt,
затем выполняет `readback`. Алгоритмы материала, маршрута, ориентации, DoubleML,
прочности и шума не дублируются в оболочке. При сборке/установке сохраняется
точная копия исходного ядра; контрольные суммы — в [core_identity.json](core_identity.json).

Проверено:

- 186 тестов ядра прошли, один пропущен.
- 24 проверки оболочки прошли: для всех семи исходных STL/ТЗ решение отдельного
  worker совпадает с прямым вызовом ядра, включая статусы и объяснения;
  проверены отмена, устаревшее состояние проекта, SHA, допустимые локальные
  физические входы, запрет запоздалого Qt-callback и целостность сборки.
  Девять дополнительных регрессий проверяют ID источников, фактический путь,
  удалённый исходный файл, неоднозначный выбор и запрет угадываемых путей.
- Настоящий установленный STE 7.10.12/Python 3.5.7, отдельный профиль:
  HTTP/MCP → worker → Qt apply → отложенный readback → CuraEngine → G-code/3MF.
  Использован исходный пыльник организаторов, без изменения STL/ТЗ; STL загружен
  через HTTP в чат и передан по attachment_id. После экспорта повторное предложение
  рассчитано по object_id уже существующей сцены и имеет те же настройки/SHA.
- Нативные настройки совпали с планом. Сцена, настройки и геометрия восстановлены
  Undo/Redo; вся операция занимает одну запись истории.
- Оболочка успешно выполнила пробный запрос в Timeweb/Qwen с ключом из локального `.env`.
  Ключ не возвращается через `/api/state`; точного значения ключа нет в сохранённых
  G-code, распакованном 3MF и readback.
- Оценка штатного движка: 86 618 с, 56,68 м / 156,8 г TPU. Это расчёт движка,
  а не измерение времени/массы реального отпечатка. Заголовок G-code содержит
  86 617 с и 56,6788 м; округлённое представление UI согласуется с ним.

Машиночитаемый результат и SHA нативных артефактов:
[native_report.json](native_report.json). Сами локальные сессии, токены, профили,
виртуальные окружения и `.env` не публикуются.

В процессе проверки исправлены только связи оболочки с API STE: штатные writers
G-code/3MF могут ждать Qt-callback, поэтому вызываются из фонового потока;
изменение служебного id контейнера после apply не считается изменением геометрии.
Контроль значений остаётся в исходном `readback`.

Исправлена воспроизведённая ошибка `Select an existing absolute STL path`:
список объектов раньше возвращал только имя, и Qwen угадывала папки. Теперь
`list_model_sources` возвращает существующие attachment/object ID и source path,
`list_objects` включает метаданные исходного файла, а приложение само разрешает
ID в исходный STL. Несуществующий путь не заменяется поиском одноимённого файла.
При native-проверке с активным пользовательским чатом его браузерный профиль
исключается из клонирования: cookies/заблокированные browser-файлы тесту не нужны.

Документация актуализирована в [README проекта](../../README.md). Будущий выбор
совместимой полной базы native-пресетов описан в
[presets_creation.md](../../presets_creation.md) **только как промпт**. Эта
функциональность в исправление источников не включена.

Сохранившиеся ограничения:

- Пыльник остаётся `needs_input`; успешная нарезка не подтверждает герметичность,
  долговечность, абсолютную прочность или физический оптимум.
- Исходная фигурка с тиражом шесть штук не помещается с резервами существующего
  адаптера. Первый нативный запуск честно отказал; количество и логика раскладки
  не менялись для обхода ограничения. Для полного прохода выбран исходный пыльник.
- 5D apply требует кинематики и проверки коллизий, `infeasible` блокируется.
  Изолированный исследовательский `analysis_only` не доступен чатовому агенту.
- Автоматический FE-поиск по повторным native-слайсам остаётся отдельным
  исследовательским API/CLI. Синтетические данные не используются как подтверждение
  качества реальной печати или как новые измерения для DML.
