# AI Assistant для STE Slicer

Плагин добавляет в STE Slicer 7.x (форк Cura 3.6, `"api": 5`) окно чата с LLM. Пользователь пишет задачу и
прикладывает модель STL/OBJ/3MF или фото JPG/PNG. Для ТЗ + STL агент вызывает существующее ядро
`ste_planner.plan_case`, затем его Qt-адаптер. Выбор материала, режима, ориентации, настроек,
DoubleML и оценка неопределённости сохраняют исходные алгоритмы. Ручные инструменты Lenaz,
чат, темы, RU/EN, профили, работа с OBJ/3MF и MCP доступны как прежде.

## Установка

1. Из корня проекта запустите современным Python с установленными зависимостями:
   `python plugin/tools/install_ai_assistant.py --python "C:\path\to\python.exe"`.
   Скрипт собирает оболочку с точной копией `plugin/ste_planner`, проверяет SHA-256,
   устанавливает в `%APPDATA%\steslicer\7.10\plugins\AIAssistant` и сохраняет резервную
   копию предыдущего плагина в `.runtime`. Для другой версии передайте `--profile`.
2. Перезапустите STE Slicer.
3. Меню **Расширения → AI Assistant → Open chat**.

`git pull` обновляет репозиторий, а установленный плагин находится в отдельной
папке. После обновления исходников повторите установщик и полностью перезапустите
STE: перезагрузка вкладки чата не перезагружает Python-расширение. Сохраните текущий
проект перед перезапуском; пересоздавать его для работы с объектом не требуется.

Чат открывается панелью внутри окна слайсера (Windows, Edge или Chrome в режиме приложения).
Справа резервируется полоса: интерфейс STE получает отступ, 3D-вид сужается до оставшейся
части, ничего не перекрывается. Окно браузера стоит точно в этой полосе без своего заголовка
и рамки, принадлежит окну STE (всегда над ним, сворачивается вместе с ним, без кнопки на
панели задач) и следует за перемещением и размером. Ширину меняет ручка слева от панели,
значение запоминается. **Расширения → AI Assistant → Hide chat** скрывает панель и возвращает
слайсеру всю ширину; повторный **Open chat** показывает её без перезапуска браузера.

Почему не встроенный веб-вид: в PyQt дистрибутива STE нет QtWebEngine, и из плагина его не
инициализировать. Почему не дочернее окно (`WS_CHILD`): Chromium в таком окне не получает
ввод с клавиатуры. Для профиля чата отключены DirectComposition (иначе заголовок браузера
не обрезается) и `CalculateNativeWinOcclusion` (иначе после сворачивания страница не
возвращается). При первом запуске нового профиля Edge может один раз показать подсказку о
входе в учётную запись поверх чата — её достаточно закрыть.

Если разметку STE не удалось распознать, чат открывается прежним способом — отдельным окном,
прикреплённым справа к окну слайсера. Без Edge/Chrome чат открывается обычной вкладкой
системного браузера. Ручная проверка встраивания на Windows:
`python plugin/tools/check_embedded_chat.py` (PyQt5 и Pillow; один клик в поле чата и три
нажатия клавиш, только если в точке клика окно чата).

## Настройка LLM

Кнопка `⋯` в окне чата → **Настройки**:

- **URL API** и **Модель** — выданные организаторами (по умолчанию `https://api.timeweb.ai/v1`, `dashscope/qwen3.8-flash`);
- **Ключ API** — вводится здесь и хранится в настройках приложения (`steslicer.cfg`, раздел `ai_assistant`), в код не попадает
  и в окно чата обратно не передаётся. Установщик также подключает локальный корневой `.env`:
  его путь хранится в непубликуемом `local_config.json`, ключ читается только в память.
  Поддерживаются `TIMEWEB_API_KEY`, `LLM_API_KEY`, `QWEN_*`/`LLM_*` URL и модель;
- **Python ядра** — абсолютный путь к современному Python, например `.venv-functional\Scripts\python.exe`.
  Зависимости worker: `experiments/functional_requirements.lock.txt`; Python 3.5 слайсера не изменяется;
- **JSON измерений, нагрузок и шума** — необязательный локальный файл с ключами
  `calibration_data`, `functional_spec`, `noise_spec`, `robustness_limits` в существующих форматах ядра.
  Эти данные задаёт приложение/инженер, агент не может подменить их через аргументы инструмента.
  Без измерений сохраняются статусы `needs_input` / `needs_calibration`;
- **Папка** для G-code и проектов: по умолчанию `Документы\STE AI Assistant\<имя задания>\result.gcode` и `project.3mf`;
- язык интерфейса RU/EN и тема (светлая/тёмная).

**Проверить** отправляет пробный запрос к модели.

## Как это работает

```
SPA (web/: HTML + CSS + JS)
   │  HTTP на 127.0.0.1, long polling для потоковых событий
Python-плагин: agent/agent.py — цикл диалога с LLM (Chat Completions, стриминг, tool calling)
   │ tools/call                         │ OpenAI-совместимый API
agent/mcp.py — MCP-сервер (JSON-RPC 2.0)   LLM
   │
agent/core_bridge.py → современный core_worker.py → исходный ste_planner
   │ application-owned plan_id, SHA исходного STL, отмена/устаревание
agent/tools.py → runtime_adapter.create_operation / readback в Qt
   │ штатные движки STE и writers G-code/3MF
```

Обычный маршрут: `plan_print → apply_plan → verify_plan → slice → export_gcode → save_project`.
Перед ним `list_model_sources` показывает прикреплённые модели и исходные файлы
объектов сцены. В `plan_print` указывайте ровно один источник: `attachment_id`,
`object_id` либо существующий абсолютный `mesh_path`. Qwen не должна угадывать путь.
Модель сначала не загружается вручную. Для прикрепления Qt-operation загружает исходный
STL в пустой проект; для `object_id` переориентирует уже загруженный объект. Сцена и
профиль меняются одной операцией Undo; существующие детали автоматически не удаляются.
При смене файла, проекта или входных измерений
план пересчитывается. Отмена завершает worker и делает его plan_id недействительным.

Для переносимого архива: `python plugin/tools/build_ai_assistant.py --output .runtime/release/AIAssistant`.
В такую сборку не входят `.env`, `local_config.json`, виртуальное окружение и эксперименты.
Настройте Python/ключ после копирования. `bundle_manifest.json` подтверждает точную копию ядра.

### Порядок работы агента

0. **Вопрос или задача.** Явные вопросы («почему так долго», «какой сейчас пресет?», «как уменьшить
   время?») и явные просьбы («ускорь печать», «можешь повернуть деталь?») определяются локально.
   Для неоднозначной фразы короткий вызов модели учитывает контекст диалога. Ошибка, таймаут,
   пустая или некорректная классификация оставляют **режим ответа без инструментов**.
   Модель получает снимок `get_state`, `list_profiles` и, если слайс уже готов, `get_slice_result`;
   новый слайсинг для объяснения времени не запускается. В API-запросе ответа нет списка tools,
   задано `tool_choice=none`. Сначала даётся объяснение; карточки выбора и изменения недоступны.
   Вложение не меняет вопрос на задачу; отправка модели/ТЗ без текста означает подготовку задачи.
   Старые команды и содержимое вложений не подменяют исходный текст текущего сообщения.
   В смешанной просьбе «почему долго? уменьши заполнение» остаётся режим действий.
   [Регрессии и живая проверка Timeweb](../experiments/question_routing/README.md).
1. **Чтение среды.** В начале работы по задаче приложение само вызывает `get_state` (принтер, режим,
   активный пресет, экструдеры и сопла, ключевые настройки, объекты сцены), `list_model_sources`
   (прикреплённые файлы и исходники объектов) и `list_profiles` (установленные пресеты). В чате это
   один шаг «Читаю проект, пресеты и вложения»; результаты попадают в историю модели.
2. **Чтение вложений.** STL/OBJ/3MF, фото JPG/PNG (`image_url`, base64) и ТЗ **DOCX/TXT/MD**: текст ТЗ
   извлекается той же функцией, что у ядра (`read_docx_text`), и передаётся в `plan_print` по
   `spec_attachment_id` без пересказа.
3. **Пресет под систему.** `plan_print` выбирает совместимый штатный пресет STE и минимальный Δ
   (см. ниже). Если пресет не подобран (`needs_input`, например материалу нужно сопло 0.6 мм),
   агент задаёт вопрос с вариантами ядра; после ответа — `set_nozzle` или `preferred_material` и новый расчёт.
   Отказ показан компактной раскрываемой плашкой: материал, режим и причина на русском
   («Нужно сопло от 0,6 мм; установлено 0,4 мм»). Рекомендации раскрываются нажатием.
   Другие отклонённые профили доступны в разделе «Отброшенные пресеты»; исходные диагностики
   ядра сохраняются в подробностях вызова, перевод не меняет проверку совместимости.
   **Уточнения — в начале и разом:** когда пресет выбран, а данных не хватает (какая катушка стоит,
   нагрузка, температура), агент задаёт все вопросы одним вызовом `ask_user` (до 6) и, если ответы
   меняют задачу, пересчитывает план с ответами пользователя.
4. **Переход к выполнению.** После расчёта и объяснения готового плана приложение показывает
   «Перейти к выполнению / Остаться в планировании». До ответа изменения по плану не выполняются.
   Это проверка в агенте, а не только инструкция модели: отказ завершает ход и отменяет оставшиеся
   вызовы даже в одном пакете. Одно согласие переводит текущую задачу в выполнение до конца:
   применение, проверка, слайсинг и сохранение. Повторный расчёт той же задачи, новый ID плана,
   повтор после ошибки и применение только настроек к проекту не открывают новую карточку.
   Модель получает актуальный ID одобренного плана и читает его через `get_plan`, не пересчитывая
   ради чтения. Во время выполнения `ask_user` убран из списка инструментов; даже устаревший
   вызов не откроет повторный вопрос. Можно выбрать кнопку или
   написать безусловное «да»; ответ с условием («да, но сначала поменяй материал») не запускает план.
   Неподходящий пресет или невыполнимый план не предлагается к выполнению. Обычный вопрос не
   открывает подтверждение; явная ручная команда без расчёта плана выполняется обычным инструментом.
   Пустой проект или одна модель на столе — `apply_plan` (точная ориентация,
   положение, пресет, одна операция Undo). Несколько моделей или пользователь не хочет двигать деталь —
   `apply_plan_to_project`: первоначальная карточка предупреждает об общих настройках всех моделей;
   в проект ставится тот же пресет и Δ, детали не двигаются
   (одна операция Undo, проверка readback, `revert_plan_changes`). Явные просьбы пользователя
   («максимально прочно», «заполнение 30 %») доводятся ручными инструментами поверх пресета.
   Новая задача пользователя начинает новый переход. Подмена материала, режима или исходной
   модели во время выполнения не получает согласие автоматически: агент должен сохранить
   согласованные условия и исправить расчёт. Если обязательного физического факта нет, он
   сообщает препятствие, а не выдумывает ответ за пользователя.
4a. **Проверка положения — всегда.** Перед нарезкой, экспортом и сохранением (а если нарезки в ходе не было — в
   конце хода с правками) приложение само проверяет позу каждой детали на столе (`optimize_orientation`, только 3D).
   Расчёт ядра в текущей позе даёт её оценку, лучшую позу и кандидатов. Жёсткость позы берётся из FE-модели ядра,
   если входные данные планирования задают для детали нагрузки, закрепления и константы (податливость); иначе — из
   аналитической оценки ядра (доля нагрузки поперёк слоёв), и агент говорит, что FE не считался. Время и пластик —
   нарезкой обеих поз. Правила (порог 5 %): поза мягче текущей больше чем на 5 % не принимается; лучшая поза ядра
   принимается, если экономит ≥ 5 % времени или пластика (другое хуже не более чем на 5 %); поза жёстче на ≥ 5 %
   принимается, если время и пластик хуже не более чем на 5 %; на просьбу «прочнее» — самая жёсткая поза; позу,
   заданную пользователем («не поворачивай», `rotate_object`, `keep_current`), не меняет и только сообщает выигрыш.
   Поворачивается только деталь на своём месте (одна операция Undo), пресет не трогается; если детали после
   поворота задевают друг друга или выходят за стол — расставляются.
4b. **Материал не задан.** Если ни ТЗ, ни пользователь не назвали материал (или просят «другой материал» без
   названия — тогда текущий исключается), агент вызывает `compare_materials`: 3 лучших подходящих материала ядра,
   каждый со своим пресетом, применяются, нарезаются и откатываются. Карточка показывает их со временем и
   расходом; выбранный пересчитывается и применяется, а выбор считается согласием на выполнение (без второй
   карточки «Перейти к выполнению?»). Свой ответ в карточке уходит агенту текстом.
5. **5D.** Ядро не проверяет кинематику и коллизии 5D; применение 5D-плана возможно только после
   предупреждения в той же карточке перехода и согласия пользователя. Агент выставляет
   `confirm_unverified_5d=true` только после фактического ответа; без подтверждения блокировка
   ядра сохраняется. Это не подтверждает физическую пригодность к печати.
6. Слайсинг, экспорт G-code и проекта 3MF, короткое объяснение решений.
7. **Проверка текста.** Итоговый ответ и тексты вопросов проверяет второй вызов модели. Ответ сначала
   показывается как есть и заменяется, только если в нём грубая ошибка: не тот род или падеж, слова
   склеены из русского и английского, попали иероглифы. Исправление отбрасывается, если в нём
   изменились числа или длина текста (факты не трогаются).

### Что видно в чате

- шаги, а не отдельные вызовы: подряд идущие действия складываются в одну строку с фразой ИИ
  («Подбираю пресет и настройки на прочность»), под ней список вызовов (`Поиск настроек ×3 · …`);
  новая строка — только при новой фразе ИИ или смене фазы (настройки → расчёт → нарезка);
- ход мыслей свёрнут; по `⋯` — мысли, каждый вызов с аргументами и JSON результата, ошибки и
  отметка «исправлено повтором»; нерешённые ошибки видны сразу;
- карточка пресета у расчёта ядра: пресет STE, материал, режим, статус и изменения поверх пресета
  с причиной (по ТЗ, ограничение, класс нагрузки), пунктиром — это ещё предложение;
- неподходящие пресеты — небольшие плашки с причинами на языке интерфейса; рекомендации скрыты
  до раскрытия, поэтому несколько попыток подбора не загромождают чат;
- применённые изменения подсвечены: «Пресет STE Normal → **Fine (normal)**», «Плотность заполнения
  20% → **60%**»; значения, сброшенные к пресету, отмечены светлее; те же значения сразу меняются в STE;
- вопросы агента — одна карточка-мастер «2 / 4 ‹ ›»: варианты (рекомендуемый первым) и серое поле
  «Свой вариант…»; ↑↓ — выбор, Enter — ответ и следующий вопрос, ← → — назад и вперёд; в конце экран
  «Проверьте ответы» с кнопками «Отправить» и «Изменить» (строку можно нажать и вернуться к вопросу).
  Текст из обычного поля ввода становится своим ответом на текущий вопрос; при пустом поле кнопка
  справа — «стоп». Выбранные ответы переживают перезагрузку окна. После отправки в чате остаются все
  вопросы и ответы. Агент не спрашивает то, что уже решил расчёт ядра (режим, изменения настроек), —
  физические условия: какая катушка стоит, нагрузка, среда, критичные размеры. Готовый план
  требует отдельного согласия на переход к выполнению;
- кнопка-ветка — дерево моделей чата. Модель — это настройка печати: пресет и контейнеры стеков,
  значения пользователя поверх, режим 3D/5D и положение деталей на столе. Она сохраняется, когда агент закончил
  ход и что-то изменил (промежуточные состояния не сохраняются, ответы на вопросы — тоже). Если оценки нет,
  модель сначала нарезается, чтобы у узла были время и пластик. Имя (1–3 слова) даёт модель, в кружке —
  сокращение («Быстрая печать» → «БП»). Время идёт сверху вниз: старые узлы сверху, новые ниже, ветки
  расходятся симметрично от родителя. При наведении слайсер показывает карточку слева от чата над столом: название,
  строку «3D/5D · время · пластик · заполнение» из сохранённого состояния этого узла,
  и до 10 изменений относительно предыдущего узла: сначала режим, пресет, материал, сопло и
  положение деталей, затем настройки, изменённые явно («явно»), затем главное, что сдвинулось вместе с
  пресетом («пресет»); остальное — строкой «и ещё N». Сравниваются все включённые параметры, не только основные.
  Клик переключает слайсер на этот узел (одна операция Undo), а чат — на его ветку: лента и память модели
  становятся разговором от начала до сообщения, создавшего узел, плюс вопросы-ответы после него, если новой
  модели после них не было. Новое сообщение растёт новой веткой от выбранного узла; другие ветки сохраняются
  и открываются кликом по своим узлам («Исходная» — разговор до первой работы). У каждого чата своё дерево:
  при открытии чата слайсер и лента переходят на узел и ветку, выбранные в нём последними. Первый узел «Исходная» — проект до первой работы в чате;
- кнопка с часами — сохранённые чаты (сегодня / вчера / дата). Чат можно открыть и продолжить: лента и
  история модели восстанавливаются (без изображений). «+» сохраняет текущий чат и начинает новый.
  Чаты лежат в папке данных STE: `ai_assistant_chats/*.json`, рядом — прикреплённые в чате модели и ТЗ
  (`<id>.files/`), так что по старому чату можно считать и после перезапуска; удаление чата удаляет и их.
  Агенту видны только вложения текущего чата. Чат, сохранённый при закрытии слайсера посреди работы,
  открывается с отменёнными вопросами и прерванными шагами;
- прогресс слайсинга и итог: время печати и расход материала; пути сохранённых файлов;
- у файла, который не прикрепился, указана причина: формат, пустой файл, больше 300 МБ, не читается
  (например, перетащен прямо из ZIP), не удалось прочитать текст ТЗ, нет связи.

## MCP

Инструменты доступны и внешним MCP-клиентам: `POST http://127.0.0.1:<порт>/mcp` (JSON-RPC 2.0: `initialize`,

настроек чата. Вызовы внешних клиентов отображаются в чате с пометкой «MCP».

## Ошибка пути к STL

`Select an existing absolute STL path` означает, что в расчёт передан несуществующий
или относительный путь либо неподдерживаемый формат. Например, имя `Шестерня.stl`
на столе слайсера ещё не является абсолютным путём. В старой оболочке список объектов
не отдавал исходный файл и Qwen пыталась угадывать папку; это исправлено.

Прикрепите STL скрепкой в чате и используйте `attachment_id`. Для существующего
объекта `list_model_sources`/`list_objects` показывают его ID, `source_path`,
`source_exists`, `source_format`, `can_plan_original_stl`; `object_id` разрешается
приложением в фактический исходный STL. Если файл удалён/перемещён или объект
получен из OBJ/3MF без оригинального STL, прикрепите исходный STL. Никакого поиска
одноимённого файла по диску и автоматического выбора среди неоднозначных источников нет.

Расчёт по объекту использует оригинальный файл, а не текущий transform сцены.
Если модель уже на столе, расчёт по её `object_id` применяется к этому же объекту:
`apply_plan` проверяет, что его меш совпадает с исходным STL (те же грани в порядке
STL-ридера), и одной операцией Undo заменяет его поворот/положение/масштаб плановыми,
переводит на экструдер 1 и добавляет копии тиража и модификаторы. Undo возвращает
объект как был. Других моделей в проекте быть не должно: план пишет глобальные
настройки, которые изменили бы и их; собственные модификаторы и per-object настройки
объекта тоже блокируют применение. Для прикреплённого файла по-прежнему нужен пустой
проект: `apply_plan` загружает его сам. Существующие детали плагин не удаляет.
`get_plan` показывает это в `apply_target`. Проверено тестами контрактов
(`shell_tests/test_scene_target.py`) и в настоящем STE 7.10.12 на исходном пыльнике:
ручные перемещение/поворот → план по object_id → тот же объект → native-пресет →
readback → slice → экспорт → точный Undo/Redo.

Штатный импорт STE центрирует вершины. Адаптер принимает исходную или именно
такую центрированную сетку, компенсируя перенос в матрице объекта и модификаторов.
Повреждение геометрии и неучтённые масштабы/деформации не маскируются сопоставлением.
`get_state`/`list_objects` передают также мировую матрицу в осях принтера;
положение сохраняется в JSON до 0,001 мм, чтобы смещение 0,05 мм не терялось.

## Пресеты STE как база плана

`plan_print` передаёт ядру снимок установленных принтера, сопел, материалов и профилей.
Ядро выбирает совместимый штатный профиль, наследует его настройки и меняет только
обоснованные ТЗ параметры; `get_plan` показывает выбранный профиль (`base_preset`) и
список изменений (`setting_changes`) без внутренних id контейнеров. Без совместимой базы
план получает `needs_input` с вариантами и не применяется. Пользовательский профиль
участвует только при явном разрешении в `local_config.json`
(`allowed_quality_changes`); `native_presets: false` возвращает прежний
`Planner process profile`. Подробности: [PRESETS.md](../plugin/PRESETS.md).
Native-база и её readback проверены в настоящем STE 7.10.12. Служебные None-записи,
которые STE лениво удаляет, не считаются overrides и не дают ложного устаревания.

Уточнения нужны для данных, которых нет в пресетах: доступность реального пластика,
условия эксплуатации, нагрузки/направления/закрепления, важные допуски. Уже заданные
в ТЗ или подтверждённые пользователем сведения повторно не запрашиваются.
Текст DOCX не затирает сопроводительную просьбу, например «не менять положение».

Пресет в уже открытый проект: `apply_plan_to_project` вызывает
`runtime_adapter.create_settings_operation` — те же проверки базы (контракт, машина, хеши
контейнеров P, согласованность Δ с ожидаемым readback), реальные контейнеры P в стеки и Δ в
user-контейнер одной операцией Undo, readback обязан пройти. Ручные изменения пользователя,
которых нет в Δ, заменяются значениями пресета и показываются в чате.

Ограничения: 5D рассчитывается как предложение и применяется только после явного согласия
пользователя (`confirm_unverified_5d`), с предупреждением, что кинематика и коллизии не проверены.
`infeasible` не применяется.
Полный тираж фигурки из примера 4 сейчас не помещается с резервами адаптера; оболочка
показывает отказ и не уменьшает количество автоматически. Физический оптимум, прочность
и устойчивость не подтверждаются самим фактом успешной нарезки; `physical_print_approval=false`.
Отдельные `toolpath_physics.analyze_slice` / `sliced_search` и их 5D протокол остаются
доступны через существующий worker API/CLI, их автоматический FE-поиск не запускается чатом.
Ядро возвращает поля тензора напряжений, объёмного давления и нормального давления
на гранях для заданной линейной краевой задачи. Это не контактный расчёт и не
давление расплава; без свойств материала, нагрузок и кинематики они не подтверждают
напряжения реального 5D-отпечатка. [Проверка и формулы](../experiments/pressure_validation/README.md).
